# Authoring skills

What a skill should contain and how it should read. Run the skill-creator plugin when you want evals or description benchmarking (disabled by default; enable it for the run); this is the judgment layer on top. The dates, quotes and sources behind these rules live in `references/learnings.md`; no step needs to read it.

## Harness principles

conor-os is the harness around the model for zero-to-one work: Claude Code runs the loop, and these skills decide how work gets planned, judged, remembered and improved. Five principles hold across every skill. Check a new skill or an import against them.

- **State lives in files.** Ledgers, learnings, docs and the tracker carry work between sessions and agents. The conversation compacts and forgets.
- **A judge doesn't see the maker's case.** Critics and reviewers get the artifact and the bar (the criteria it's judged on), never the brief's reasoning or the maker's report, so a claim can't argue its way to a pass. The one addition: a scoring critic may get the user's standing calls as a do-not-raise list, since re-flagging a settled call wastes a round. A blind comparison gets none, since the calls point at ours.
- **Every rule predicts something.** A new rule names what should look different in the next runs. A rule you can't write that for is too vague to follow.
- **Failures are kept with the reason.** Misses, rejected findings, failed prompts and losing directions get written where the next run reads them. A record of only what worked repeats what didn't.
- **Agents propose, the user decides.** A change to how we work lands after the user's yes in chat, or because the user stated the rule. The PR itself then merges without a review from the user (Merging a skills PR). A bare "continue" resumes the talk, it isn't a yes to proposals. zero-to-one's orchestration and brand-design's three boards change only on a yes by name, except to fix a broken link or a wrong name.

## What goes where

- **CLAUDE.md**: applies to every session regardless of task. Communication preferences, hard rules, formatting defaults. Target well under 200 lines; every line should be one that, if removed, would cause a mistake.
- **A skill**: applies to a specific kind of work. Loads on demand, so it costs only its description until it's relevant. Multi-step workflows, output formats, domain judgment.
- **Personal vs. work repo**: the personal repo holds how Conor thinks and writes (formats, voice, what to cut, checklists). The work repo holds where things go and what they're called (database IDs, tool names, channels, strategy docs, agents). A personal skill should never contain an ID, a channel name, or a person's name. A work skill that needs the personal judgment copies it in (cloud and scheduled runs don't have personal skills), after the rule lands here first.
- **Personal skills vs. a project repo**: the same split one level down. A project's CLAUDE.md, docs, ledgers, and memory hold that project's facts; a rule that would hold on another project goes in the skill that owns the step. A project file may carry a copy of a skill rule its sessions need (CLAUDE.md for implementers who never load the skill), but the skill is the source and changes land there first.

## Tickets, merging and hooks

- **An idea for conor-os gets a ticket.** When the user brings an idea for improving conor-os (an article, a tool, a pattern from another project) and the talk reaches concrete changes, a new direction, or a not-worth-encoding verdict, file it unasked in this repo's improvements project in Linear with the fields global CLAUDE.md requires, labeled by kind (Improvement, Feature, Bug, Research). The description holds their context and links, what we already do, the proposals, and the decisions owed. A passing question or a one-line fix doesn't need one; an idea we may never ship does, since the board records what we considered.
- **Its state follows the talk.** Waiting on Me only while a decision is owed (a chore on the user's side isn't one: do it yourself, or say so in the Done note). In Progress once they answer. Done when the pick ships, noting the proposals passed on and relabelling if the kind of work changed. Canceled when nothing ships, a not-worth-encoding verdict included, with the reason. A PR that doesn't finish the ticket keeps its key out of the title and branch, since merging it closes the ticket.
- **Picking up a ticket.** Work only the ticket the user named, one at a time, with findings on it. Don't ask why it was filed (the intent is always a better conor-os): research it and lead with the verdict (Importing). One filed offhand (a bare link, a guessed title) gets retitled once you've read the source, to say what it's about, and a short description: what the link is, why it might matter, the question it raises, link kept.
- **Merging a skills PR**: the agent merges its own conor-os PR once the cold read's seams are fixed; Conor doesn't review each one. From a project session whose hooks guard merges, name the repo (`gh -R <owner>/conor-os pr merge <n> --merge`) so the hook sees it isn't the project's PR, then pull the live checkout so `~/.claude/skills` picks it up.
- **The Linear hook**: `scripts/linear-issue-fields.py`, a PreToolUse hook in `~/.claude/settings.json`, blocks a `save_issue` create missing any of those fields.
- **The public edition**: a weekly task publishes a public copy of this repo. A new skill ships by default: ask the user at creation, and mark a private one so the edition leaves it out.
- **The commit hook**: a pre-commit hook blocks a commit `skill-budget.py` fails. A fresh worktree runs `vendor-sync.py` first.

## Closing a skill update

The skill pause: one name and one procedure for every skill, at every pause (a surface close, a milestone, a run's end, a handoff, a correction batch). A skill's own pause section says only which lesson goes in which of its files. A correction or pick given mid-run is folded into its owning skill in the turn it's given, even mid-skill, without being asked; the pause only sweeps what that missed. Every rule and pick lands with its reason, so the next run can extend it to new cases; when the user gave none, the pick lands now and a proposed reason waits for a yes.

1. **Sweep the run.** Every correction, pick and accepted critic finding from the whole run (resolved threads and early rounds too) becomes a principle in the skill that should have caught it (Encode a correction one level up), its dated case in `references/learnings.md` or its archive. Trace a "we covered this" to the step that didn't read the rule, and fix that step first. Prune as you add.
2. **Check.** `python3 -I skills/authoring-skills/scripts/skill-budget.py`, fixing what it fails, plus `/doctor` when interactive.
3. **Cold read** (below) on every skill the pause edited.
4. **Report.** The diff, then a five-part summary: what changed where, principles from feedback, process changes, what the critics taught (where they converged, where the user overruled them), what you'll do proactively. A rule the user stated lands as stated; one they didn't state waits for their yes.
5. **Ship.** Commit, push and open the PR in the same turn, then merge it (Merging a skills PR). A rule the user stated ships now; one you inferred waits for their yes, in its own PR if the stated one is ready first.

## Size and frontmatter

- **Measure a body in words, not lines.** SKILL.md aims under ~3,500 words (~5k tokens) and never passes 4,000, because compaction keeps only the first 5,000 tokens of an invoked skill and never re-reads the file, so in a long session the back half of a bigger body silently disappears. Put the rules that must survive near the top and the parts a session can lose (checklists, rare branches) at the end, and move step-specific detail into `references/` read at that step. References link one level deep from SKILL.md, never chained; one over 100 lines gets a table of contents.
- **Always-read references get a word cap.** A file a skill reads in full every run (preferences, constraints, learnings) stays under ~1,500 words. SKILL.md marks each by writing "every run" (or "every surface" for a per-surface loop) right after its backticked path, as build does for its learnings, and the script measures exactly the marked files; a step reference (a template, a catalog) isn't marked. Past the cap, the oldest or narrowest entries move to `references/<file>-archive.md` with their dates, and the always-read file keeps the rule. The script checks each file's cap, not how many a step reads; the cold read catches that. A step that reads more than two such files merges them or stages them so each is read at the step that needs it.
- **`description` is triggers, not a table of contents.** One sentence on what the skill does, the phrases a user actually says, and the neighbors to refuse ("Do NOT use for X (Y)"). Third person, key use case first, all "when to use" here and none in the body. Claude tends to under-trigger, so be pushy with trigger phrases, never with a summary of the body. Target under 550 chars, hard cap 1,024: the skill listing gets 1% of the context window, shared with every plugin, and when it overflows Claude Code drops descriptions, so the skill can't trigger.
- **Invocation.** `user-invocable: false` for background knowledge nobody would type as a command. `disable-model-invocation: true` only for workflows with side effects that only the user should start (deploy, send, post); it removes the description and blocks the Skill tool, so no other skill can call it either. A vendored judge a skill calls can't keep it: drop it with a `frontmatter` override in `vendor.json`, or the caller reads its SKILL.md by path. A skill that's only called by another skill or by name gets `"<name>": "name-only"` under `skillOverrides` in `~/.claude/settings.json` instead: listed by name with no description cost, still callable by the Skill tool and `/name`.
- `name` matches the directory name: lowercase, hyphens, under 64 characters.
- `allowed-tools` to pre-approve the tool calls a workflow always makes, so it doesn't prompt mid-flow.
- `metadata` credits an adapted skill (`adapted-from`, author, license). A vendored skill's provenance lives in `vendor.json`.
- No per-skill README. The repo's top-level README is the directory, and a README that restates SKILL.md drifts.
- `scripts/skill-budget.py` checks these caps and totals the listed skills' description chars. Its header lists the other checks (README rows, Contents lines, `Model:` lines, spelling, agent YAML); a known failure another change owns goes in its dated `ALLOWED` list, naming that change, whose PR removes the entry. Skills in `vendor.json` report without failing, except a description we override, which still has to fit the cap.

## Writing the skill

- **Only add what Claude doesn't already know.** Challenge every line. If removing it wouldn't change output quality, it's wasted context.
- **Explain reasoning, not rigid rules.** "Start with user pain because it grounds the doc in reality" beats "ALWAYS start with user pain." If you're writing MUST in caps, reframe as reasoning. Reserve emphasis for the one rule Claude keeps skipping.
- **Extract from real sessions, then generalize.** Replace specific names with roles, specific metrics with metric types, specific behaviors with categories. Test: would this help with a completely different problem in the same category?
- **Keep the research.** Research lanes that feed a skill get their raw reports committed to its `research/` folder as `YYYY-MM-DD-NN-<lane>.md`, beside the references distilled from them. No step loads them, so they cost nothing at run time, but the next update reads them first instead of starting from zero, and any value in a reference traces back to its source. New reports go beside the old ones. A product's research still goes to the project's research pages.
- **Encode a correction one level up.** When feedback lands, write the narrow reading, then ask what class of situation it belongs to, and encode the class if it holds. "Which items join the default list is your call" is one instance of "don't block Conor on sequencing or implementation calls whose effects are short-term (merged now, working later)". Keep the example as the proof, not as the rule. Stop climbing when the general version would cover cases the feedback didn't speak to.
- **A dated correction lives once.** The rule goes in the body; its date and source (the user's quote, when a correction prompted it) go in that skill's own `references/learnings.md` or its archive, with a `Predicts:` clause naming what should look different in the next runs ("preflight finds no issue without a priority"). A rule you can't write a prediction for is usually too vague to follow. The script fails a body with more than five `(2026-` parentheticals.
- **Every update prunes too.** It's easy to suggest a new rule, and nothing ever takes one out, so a skill that only grows ends up with rules that conflict. Rules written for an older model also make a newer one slower and more rigid, so tell the two kinds apart: a principle ("one focal point per frame") stays until the user changes their mind; a workaround for a model or tool weakness says what it compensates for, and is re-tested and usually cut when that model or tool updates. Every pause reads the whole skill and proposes cuts next to its additions: rules the current model follows unprompted, rules another rule already covers, a dated example whose class is now stated generally, and rules nothing in the last few runs touched. When a cut is in question, read the rule's `Predicts:` line against the last few runs: a rule the runs contradict gets reworded or cut, and one they say nothing about goes to the blind test (Testing a rule). Predictions aren't audited one by one, and no status is kept. Aim to leave the body no longer than you found it. The user's yes covers the cuts and the additions together.
- **Measure with a script, judge with a person.** Anything checkable (contrast, sizes, fonts loaded, banned words, a duration, a word count, a file existing) is a script that exits non-zero, not a prose rule the agent has to remember; prose is for what only judgment can see. A check that couldn't run is a failure, never a pass.
- **One full example beats 200 lines of section guidance.** Put it in `references/` and tell SKILL.md to read it once before drafting.
- **Match the degree of freedom to the task.** Fragile, sequence-dependent work gets exact steps. Judgment-heavy work gets heuristics and a recommendation.
- **A checklist at the end** gives Claude a feedback loop. Keep it to the things that actually go wrong, and don't repeat the body.
- **Don't say the same thing three times.** Principles, common mistakes, and checklist that all restate each other add tokens, not adherence. Pick two.
- **No em dashes in skill bodies.** Claude echoes the punctuation it reads.
- **Imperative voice, consistent terminology.** Pick one word for a thing and use it throughout.
- **Delegate by role, not by model.** When a skill spawns a subagent, name a role from `references/model-routing.md` (researcher, planner, critic, worker) and mark the line `Model:` so it's greppable. The legend and the `agents/` definitions carry the model and effort; a skill that says "Opus" goes stale the day a model ships.

## When a model ships

Every role in `agents/` pins a full model ID, and `skill-budget.py` fails when a pin isn't on the "Sweep filed for" line in `references/model-routing.md`, so whoever moves a pin files the sweep before committing. Every role on that model moves together (both Opus roles, both Fable roles).

- File a Linear issue for the sweep (Research, Todo, priority Medium, this repo's improvements project, assigned to the user), then add the new ID with its issue key to that line. Filing is the gate; running it waits for the user's go, since a full sweep is expensive.
- The sweep runs on the model that shipped, since testing what it no longer needs is the point: one lane per repo (conor-os split by area), each spawned as the role that pins the new model (a Fable release runs as `researcher`). Each lane reads the model's card and prompting guide, then its repo (conor-os first, then each product) against this prompt: "Find everything that's broken, inconsistent, inefficient, or no longer needed. Fix what you're sure about and list the rest for me to review." In conor-os that covers the skills, `agents/`, global CLAUDE.md and the memory files under `~/.claude/projects/*/memory/`. Cut workarounds the model no longer needs (Every update prunes too), retest the model notes in `references/model-routing.md`, rerun each skill's `failed-prompts.md` and `review-misses.md` cases, keep each rule in one place, and rewrite bare "never" rules to state their scope and reason.

## Testing a rule

A rule is a guess until an agent without it does worse. Test when you're not sure a rule earns its place: before adding one to a long skill (build, pr-review, hifi-design) that the model might already follow, before cutting one, or when you suspect the model does it unprompted. A rule that came straight from a correction the model just failed has its proof already. A one-line fix to a short skill doesn't need a test.

- **Blind control vs. treatment.** Pick one real case from the session that prompted the rule. Run two fresh `worker` agents with the skill as it stands and two with the rule taken out, given the same inputs and told nothing about the test (Model: worker role). Run once; when a group splits within itself, run both groups again, since an intermittent break can show up in only one run of two. When the skill keeps a misses log (pr-review's `review-misses.md`, hifi-design's `failed-prompts.md`), add one or two past misses as extra cases.
- **Grade blind.** A fresh `critic` scores every output against what the correction asked for (a past miss against its recorded right answer), without knowing which group wrote it (Model: critic role).
- **Read the result.** Keep the rule when the treatment group gets it right and the control group doesn't. Cut it when both do, since the model already knows it. Rewrite it when neither does, since it's buried or badly phrased. Look at which cases flipped, not just the totals.

## Cold read

The blind test asks whether a rule earns its place; the cold read asks whether the next session can find it. Run it at every pause, on every skill the pause edited, after the edits, before the user's yes. One fresh `worker` gets only the edited SKILL.md and the references it names for those steps, plus one scenario per rule the pause added or moved, written as the situation, never the rule ("A Small issue's design loop has run five rounds and taste sits at 7. What do you do next?") (Model: worker role). The lead grades each answer against the rule it meant. A wrong or hedged answer means the rule is buried, badly phrased, or contradicted somewhere else: move it, cut around it, or split the paragraph, then ask a fresh reader again. On a fresh read, length alone doesn't bury rules: fresh readers got 36 of 36 scenarios right on build and hifi-design, paragraphs of 700 words included. What they miss is two rules that meet without saying which wins, and terms nobody defined, so write scenarios where rules meet and fix the seam, not the paragraph length.

## Importing an outside skill

Most outside skills restate ours. Before one comes in:

- Read the SKILL.md and every reference yourself; a skill is just files. List every command and script it runs and every package it installs. Writing files is low risk; installers, `npx`, and scripts that reach the network get read line by line, and are never run from a session that can push. Our pinned `vendor-sync.py` is exempt.
- Check the credits. A skill that borrows without naming its sources is a weaker signal of care.
- Find where its taste lives (fonts, colors, spacing, motion, banned patterns) and diff it against our tells and preferences. Taste that contradicts a measured rule of ours doesn't come in.
- Bring in the technique, not the skill. It lands as a reference file the owning process skill reads at its step, with the source and date, so the loop stays ours. Vendor whole only for a judge that's called at a named step (impeccable, review-animations, better-accessibility), as a `vendor.json` entry that `scripts/vendor-sync.py` installs into a gitignored `skills/<name>`, never a commit of their files. A judge installs only what its step calls (no upstream agents) and goes name-only in `skillOverrides`, so it can't fire ad hoc. Our edits stay outside them: a description override in the manifest, a map onto our skills in the caller at the step that calls it. To re-vendor, bump the pin, run `vendor-sync.py --check`, and read the diff for the files it lists before syncing. A tool we rewrite until it's ours (explain-interface) is committed like our own skills, credited in `metadata` (`adapted-from`, author, license). Check the import's frontmatter too: an upstream `disable-model-invocation` or a one-line description means it never fires on its own, so a skill that should run unasked gets real triggers and a named step in each skill that leans on it.
- **Most of what the user shares shouldn't land.** A site, article, tool or idea gets the same read: what's worth folding into our process and principles, not whether to adopt the product. Judge it from how the system works, not from who sent it: which skill would read it, at which step, and what a run would do differently. Grep the skills for each idea first; most of it we already do, so the proposal is the gap, quoted against the line that covers the rest. "Not worth encoding" is a full answer and often the right one, since every line is paid for by every future run that reads it: a playbook for a kind of product we don't build, a rule of thumb with no evidence behind it, or a rule for a case no run has hit. Say so with the reason rather than adding something so the share feels used. Two limits on that: read the real source before judging (a post's own replies usually link it, and a screenshot isn't a read), and a curated list the user vouches for as taste is reference data, not an idea, so it lands where a reference pass reads it (design-sources) rather than being judged as a rule.

## Debugging a skill

- Not triggering? Ask "when would you use the [name] skill?" and compare the answer to the description. Add the missing phrases. If the description is right but the skill still never fires, check `/doctor`: an overflowing listing drops descriptions.
- Triggering wrongly? Add the negative trigger naming the right skill.
- Output flat or generic? The skill probably cites a voice or format instead of applying it. Make the instruction "actually write in it," and add a calibration check.
- Claude skipping a rule? Late in a long session, the body's past the compaction slice and the rule sat in the back half: move it up or into its step's reference. After compaction, re-attached skills share 25,000 tokens, newest first, so the oldest of six or more can drop out whole; invoking it again restores it. Early on, it's a musty MUST or meets another rule without saying which wins.
- A step burning credits or arguing with feedback? Check the agent's pin. An unpinned subagent inherits the session model and effort, and Fable delegates readily in a harness that invites it (`references/model-routing.md`, Effort facts).
