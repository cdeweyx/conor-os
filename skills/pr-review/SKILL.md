# PR review

A reviewer that's wrong a third of the time (the seed figure, from before Opus 5.5) gets ignored, and one that merges code it didn't verify gets trusted for the wrong reasons. Precision is the whole game: the vendors that moved their numbers did it with a separate verify pass and by learning from rejections, not by finding more. So this skill narrows the brief to what breaks, runs a few independent lenses in fresh contexts, makes every serious finding quote the line that proves it, verifies each one separately, and blocks only on what survived. Style and taste belong to linters and to the user.

Read `references/lenses.md` every run, before dispatching (the reviewer and validator prompts and the finding schema), `references/lenses-milestone.md` too in milestone mode, and `references/rules.md` every run (exclusions and precedents). If the project keeps its own `docs/build/review-rules.md`, read that too; project rules win where they're more specific.

## Modes

- **Issue mode** (default): one PR, one brief. Ends in a verdict comment on the PR and, on Ready, a handoff to the project's merge script.
- **Milestone mode**: the milestone's squash commits on `main` (the build ledger's Squash sha column; at build's first hardening close, every commit from the epic's first issue up to its pin), read in a worktree pinned at the last one, while the lead works on. At build's light close it runs the bug hunts alone; otherwise all three lenses below. Adds one or two bug-hunt agents (Model: worker role; the bug-hunt prompt in `references/lenses.md`) that run the app across routes and data shapes (they found the cross-issue P1s every issue review missed; a diff-reading `/code-review max` didn't) and a drift lens (the code against the tech plan, the one-way doors as built, decisions made outside any brief, test health across the milestone, and the other direction: lines in the product doc, the decision records, or DESIGN.md that the code made wrong). Beside drift runs a structure lens: one fresh `worker` reads those commits with `references/structure.md`, the git hot spots first, and returns findings in the lens schema, P2 by default and P1 only when it names a concrete change that would break silently (Model: worker role). Issue reviews can't see it, since coupling shows up across issues. Confirmed findings go to the caller's close issue, each checked against current `main` first, except the structure lens's: it reports and never fixes, and the caller routes them (build's `references/close.md`, Drift and structure findings). What's left goes in the digest.

## The run

1. **Scope.** Write the diff to `.build/review/<n>/diff.patch` with `git diff <base>...<branch> -- . <excludes>` (base: `main`, whether or not the PR is open yet). In milestone mode, write `git show <sha> -- . <excludes>` for each of the milestone's squash shas, in merge order, since other work lands between them. The excludes keep logs, ledgers and generated files out: `':!docs/build/ledger-*' ':!docs/build/review-misses.md' ':!**/pnpm-lock.yaml' ':!**/package-lock.json' ':!**/*.lock'`, plus the baseline logs and generated tokens and types the project's review rules name (fewer tokens without losing quality). Save the unfiltered `git diff --name-status` beside it, so a changed excluded path still shows. Write the brief to a file (the Linear issue body, pulled over the Linear MCP, plus the accepted approach comment when the build ran an approach review; conformance judges the build against both). Run the project's scope script if it has one and keep its output. Run `scripts/removed-signals.sh` on the diff and save its output to `.build/review/<n>/interface-hits.txt`. Note the size; over about 400 changed lines, tell each reviewer to read in passes and say so in its report. Never paste a diff into a prompt; pass paths.
2. **The stamp runs alongside; read it, don't re-run.** In issue mode the reviewers start as soon as the head is pushed, while the implementer's check stamps it: the affected check in a milestone run (build runs the full one per merge batch), the full check for a PR that stands alone. Read the stamp in the implementer's worktree by its exit line and tail (an empty grep for a green line is a red run), and confirm the tests conformance cited ran green in it; a PR body that says green is a claim. The review never re-runs the suite. A missing stamp or a tail that looks off goes back to the caller, and the verdict waits for the fresh stamp. Running the one spec a finding names, to confirm it, is fine, in the reviewer's own scratch worktree, never the implementer's: a run queued there for the lock blocked a fix round.
3. **Review.** Size the review by the effort label first, unless the caller runs build's pre-launch weight: then one combined reviewer at any size (the numbers, copy and interface lenses below still join on their triggers), a validator only for a P0, and P2s logged, not fixed, except on a one-way-door path or a guard path the project's `docs/build/README.md` names (stored user data, auth, secrets), which gets the full set at either weight. Small or Medium gets one combined reviewer (conformance's test-diff section plus correctness's checklist, minus correctness on a low-blast-radius diff as defined below), plus the copy reviewer when the diff rewrites user-facing words. The numbers lens joins only when it touches a calculation, and the interface lens joins at any size, only when `scripts/removed-signals.sh` printed something. Large, a one-way-door path or a protected path gets the full set below. Dispatch the reviewers in parallel, each a fresh `worker` with the diff path, the brief path, CLAUDE.md, and the rules files, never the session history, the PR body, or the implementer's report, since a description that frames a change as safe walks real bugs past reviewers (Model: worker role; reviewers are told they're read-only, and `git status` must be clean after they return). Always: brief conformance (which runs its test-diff section first). Add correctness unless the diff is low blast radius: only copy, styles, docs, or new tests, all inside the brief's Owns list, with no removed or loosened assertion. Anything touching data, a calculation, a schema, a shared contract, a migration, auth, a protected path, or a path the project's review rules mark high blast radius gets correctness, and so does anything you're unsure about. Add the numbers reviewer when the diff touches calculations, grading, counting, or golden data. Add a copy reviewer when the diff rewrites user-facing words (the copy prompt in `references/lenses.md`). Milestone mode adds the drift and structure lenses, except at build's light close, which runs the bug hunts alone. Each returns findings in the schema in `references/lenses.md`.
4. **Verify.** One fresh `worker` validator per P0 or P1 finding (P0 only on Small or Medium and at pre-launch weight, outside a one-way-door or guard path, where a P1 stands on the reviewer's repro or quoted line), given only that finding, the diff path, and repo read access (Model: worker role). One per finding, never batched: a batched validator pattern-matches across findings and becomes a second reviewer. It returns confirmed, rejected, or unresolved with the line it cites. P2 findings aren't verified, and anything a linter owns is dropped.
5. **Verdict.** Dedupe. A confirmed or unresolved P0 means Not ready; unresolved stays a gate and is never cleared silently. A confirmed P1 means Ready with fixes, unless step 6 lets it carry. Otherwise Ready. Post one comment on the PR: the verdict line exactly as `Verdict: <Ready | Ready with fixes | Not ready> @ <head sha>` with the stamped head's full sha (the merge script parses it), and it opens the comment: the merge script reads only a first-line verdict, so a hold note goes under it. Under it go the check output tail, the conformance table, at most five findings with their quoted lines ("plus N more" past that), and the declined-to-judge list. That comment is the review's record on the PR: no inline comments, no posted lens reports.
6. **Fix loop.** On Ready with fixes or Not ready, the caller resumes the implementer with the confirmed findings. Re-review is scoped: the same lenses on the new commits plus each prior finding marked addressed or not ("attempted" isn't addressed). A head that moved after the review for another reason (a merge-in) gets the same scoped re-review before the verdict. At the caller's fix-round limit (counted in fix rounds, not reviews; build's Standing rules own it; two by default), label the PR `needs-human`, post a comment that opens with the decision needed from the user and the review's take on it (then the unresolved findings), and stop; authors and reviewers stop converging after a couple of rounds and start trading concessions. A P2, or a P1 whose fix is a baseline reason, a doc line or a ruling, can carry to the next PR through the same code when that PR is already filed in this milestone: the verdict says Ready, names each carried item, and the caller puts them in that PR's brief and logs a ruling. A P1 in product behavior never carries.
7. **Hand off.** On Ready, the caller runs the project's merge script. This skill never merges and never approves on GitHub.
8. **Learn.** See below. Every run, not at the end of a milestone.

## What it learns, and where

Two files in this skill and two in the project. The split follows the house rule: how to review lives here, what this repo's paths mean lives in the repo.

- After every run, append to the project's `docs/build/review-misses.md` (create it if missing): each finding the validator rejected, each finding the implementer pushed back on with a reason the lead accepted (tagged `framing` when the PR body or the implementer's report already gave that reason, since reviewers don't read either), and the verdict. One line each: date, PR, lens, what happened. Close the run with one tally line: date, PR, and for each lens that ran (in milestone mode, each bug hunt and the drift and structure lenses too), findings raised, P0 and P1 confirmed, and of those the ones no other lens raised; a P2 sent as a cheap fix isn't confirmed. Write these lines and the tally before posting the verdict; a verdict with no log line isn't finished. The tally names the rules that fired.
- When the user later dismisses a finding (a reaction, a reply, a note after his look at a milestone) or catches something the review passed (a fix commit on reviewed code, an Agentation note on behavior the brief covered), append that too, tagged `fp` or `miss`. Misses are the valuable half; a reviewer that only hears about false positives drifts toward saying nothing.
- Propose a rule when the same pattern shows up twice, in the turn it shows up. Path-specific rules go in the project's `docs/build/review-rules.md`; rules that would hold in any repo go in `references/rules.md` here. Show the proposed line; the user's yes promotes it. Never write a rule silently, and never store an implementer's intent as a rule; store the check.
- At each skill pause (build's `references/pause.md`), sweep both rules files: flag any rule that hasn't fired in twenty reviews or drew two dismissals, and propose deleting it. Keep `references/rules.md` under 60 lines and every project rule scoped to a path glob with a date. Sum the tally lines too, and count the `framing` lines: when they outnumber confirmed findings across a milestone, propose letting conformance read the implementer's "Decisions the brief didn't make" list, never the PR body. A lens earns its agent by finding what the others miss, so one with no confirmed unique finding in fifteen runs gets proposed for folding into another lens's prompt, and the next fifteen runs check whether the misses log grows. A rule whose trigger is rare (a schema diff) counts only reviews whose diff had that trigger. The per-finding validator rests on numbers from before Opus 5.5 (a third of findings wrong, about half of subtle fakes caught): sum validator rejections and unique confirmed findings per lens from the tallies since the switch, and when validators reject under one in ten across a milestone, propose validating P0 only at every size.
- A prompt that produced a bad review goes into `references/failed-prompts.md` with what went wrong.

## Checklist

- The head's check stamp and tail were read, not the PR's claim, and the suite wasn't re-run.
- The test-diff section ran before anything else in conformance, and every removed assertion, new mock, loosened tolerance, skip, or edited golden is either asked for by the brief or a finding.
- Every finding step 4 sends to a validator got its own (P0 and P1 on the full set; P0 only on Small or Medium and at pre-launch weight, outside a one-way-door or guard path), or the verdict names the two reviewers who reproduced it; nothing unresolved was cleared.
- The verdict line is exact and carries the stamped head's sha, and the review covered every commit up to it.
- `review-misses.md` got this run's lines, and any repeated pattern got a proposed rule.
