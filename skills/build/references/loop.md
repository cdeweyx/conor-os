# The per-issue loop

Exact steps, because the order is what keeps a twelve-issue run honest. How to write the brief is in `references/brief.md`, the prompts the steps dispatch in `references/prompts.md`, the gate note and the unlock in `references/gates.md`, and the dated stories behind these steps in `references/learnings-archive.md`.

## Steps

1. **Base.** `git checkout main && git pull`, record the head sha as BASE in the ledger.
2. **Brief to file.** Pull the issue body and its comments over the Linear MCP into `.build/briefs/<KEY>.md` (gitignored) and add the lead's notes, by `references/brief.md`. Say whether the PR stands alone (step 6).
3. **Branch and worktree.** Run the project's pool script: it takes a free worktree from the warm pool under `.claude/worktrees/`, resets it to `main`'s head on the issue's `gitBranchName` from Linear (so the integration links it), and re-installs deps only when a lockfile changed. The implementer works there, never in an `isolation: worktree` copy, and the worktree goes back to the pool once its PR merges. Until the project has the script, add the worktree by hand the same way. A surface group (SKILL, preflight) uses its first issue's branch, one brief file per key, one implementer for all of them, and every key moves through the tracker together.
3a. **Readiness read (`Effort: Large`).** Dispatch the readiness prompt to a fresh reader (Model: worker role). Rule in the brief file on every choice it tags with an approach-review trigger, so step 4a starts from those rulings. Every unresolved reference gets fixed in the brief file (and on the issue, when it would mislead a later reader) before step 4. Choices tagged none stay the implementer's. Log it in the ledger line's approach field (step 11) as `ready: <choices ruled in the brief>/<references fixed>`.
4. **Implement.** Move the issue to In Progress over the Linear MCP, then dispatch the implementer with the implementer prompt (Model: worker role; effort medium for an `Effort: Small` issue, set with the Agent tool's effort parameter, and the role's high for anything bigger). When it returns, read only its status report.
4a. **Approach (flagged issues only).** For an issue that meets a trigger in the SKILL's approach review, step 4 dispatches the approach prompt first. Write its reply to `.build/approach/<KEY>.md` and dispatch a fresh tech-lead reviewer with the reviewer prompt (Model: worker role). Write a verdict per finding: accepted, accepted in part with the rejected half, or rejected with the reason (a rejection needs a fact the reviewer didn't have or a call it contradicts). Resume the implementer with the accepted findings for a revised approach. Round two, when there is one, is a fresh reviewer scoped to whether round one's blocking findings were addressed. On "sound", append the accepted approach to the brief file under "Approach (accepted)", copying the verdict's allowances word for word, post it as a comment on the issue, and resume the same implementer with "Build the accepted approach" and the implementer prompt. When the ruling splits it (SKILL, Approach review), that resume covers the first part only; each other part becomes a new issue whose body carries its slice of "Approach (accepted)" and a link to the parent, and it skips this step. Not sound after two rounds: the brief is wrong (SKILL, When to stop).
5. **Status.** DONE or DONE_WITH_CONCERNS goes on. NEEDS_CONTEXT: answer from the plan or the brief if the answer is written down and resume it; otherwise it's a wrong or thin brief (SKILL, When to stop). BLOCKED: rule on it or stop. A return or an ended session with no pushed commit on the branch is a failed dispatch: re-dispatch the same turn. A handoff names each in-flight agent's last pushed sha; "running" isn't a state a handoff can carry.
6. **Check and review, side by side, and In Review.** The implementer reports at a pushed head, before its stamp. In the same turn, dispatch `pr-review` in issue mode on that head (from `git diff main...<branch>`), move the issue to In Review over the Linear MCP (now, on the branch, not when the verdict lands; the PR-opened automation is only the fallback), and resume the implementer to run its one check there, which stamps the head; read its tail. During a milestone run that's the project's affected check (`references/project-setup.md`), since the lead runs the full check once per merge batch (step 10a); a PR that stands alone (sporadic work after launch) runs the full check, and so does every PR until the affected target and a merge script that accepts its stamp exist. Nobody else runs the suite on that head, the lead and the reviewer included (at pre-launch weight the lead's own run is the stamp, SKILL). A tail that's red or looks off goes back to the implementer with the tail. Three red rounds is a stop. Merges run one at a time, and each voids the next PR's stamp through the append-only files, so a PR whose predecessor is still merging holds its stamp until that one lands while its review runs. A head that moves after the review (a merge-in, a fix) gets `pr-review`'s scoped re-review; the verdict names the stamped head. A stop that waits on the user moves the issue to Needs Review.
7. **PR.** Once the stamp is in, open the PR into `main` with the project's bookkeeping script, which fills the PR body template (`references/prompts.md`) with the stamp's tail (until it exists, `gh pr create --base main`). Tracker moves stay on the Linear MCP.
8. **Review.** The `pr-review` from step 6 posts its verdict on the PR.
9. **Fix loop.** On Ready with fixes or Not ready, resume the same implementer with the confirmed findings only, except on a Small issue: its implementer ran at medium and an agent's effort is fixed at dispatch, so its fix round goes to a fresh implementer at high from the handoff. A fix round that needs `main`'s newer commits merges `main` in (the machine rules). Before sending a layout fix, picture it on the most common resting state, not only the state the critic flagged, since a fix aimed at one state can shift every resting one. A fix message that rules on something the approach didn't amends the brief and the issue the same turn. When the implementer's context is past about 250k tokens, the next round goes to a fresh implementer: the old one writes the handoff to `.build/handoff/<KEY>.md` first, and the new one gets it with the implementer prompt and the confirmed findings. Each fix head runs step 6 again: the scoped re-review alongside its stamp. At the round limit (SKILL, Standing rules), label `needs-human` and stop that issue.
10. **Merge.** On Ready, run the project's merge script. Run the merge script from the implementer's worktree, where the stamp lives; never copy a stamp. Gate any cleanup on its exit code (`if bash <merge script> N; then <return the worktree>; fi`): a cleanup chained with `;` once removed the worktree after a failed merge, and its implementer couldn't be resumed. Pull `main`. Make sure the issue reads Done in the tracker: Done means merged to `main`.
10a. **Batch check.** After every three or four merges, and always on the close's pinned sha before the digest (`references/close.md`, step 14), run the full `make check` on `main` inside the lock, in a dedicated detached worktree pinned to one sha, never in the lead's own checkout, since the lead pulls into that while the check runs and a pull mid-run voids it. Log it under the ledger's Batch checks. A red one is bisected across the batch's few commits with the failing target; the culprit's issue reopens to fix it, or its squash is reverted (`git revert`, never a force-push).
11. **Ledger.** The project's bookkeeping script appends one line, from what the lead passes it: key (every key, for a surface group), squash sha, changed lines, check time, approach (the trigger, rounds, and what the review changed, or "not flagged"), review rounds, peak context (ledger template), rulings, parked findings. Add anything that belongs in "For the skill".
12. **Gate?** If the README names a gate after this issue, post the gate note (`references/gates.md`) on it (it stays Done), move the issues behind the gate to Needs Review, and go on with the rest (SKILL, When to stop).
