# Parallel work

The lead reads this before fanning out a wave, and before overlapping milestones.

- **Serial by default.** The wall-clock saved for a solo builder is small and the merge-back is where bugs hide.
- **When to fan out.** Only for a wave of two or more issues that share no files, once the project's check runs on separate ports: implementers in pool worktrees, each opening its own PR into `main`, with review and merge staying serial through the lead and each branch bringing `main` in with `git merge` before it merges (never a rebase, since implementers push as they go). When two issues in a wave do touch one file, name it as a seam in both briefs. Before fanning out, list each issue's Owns side by side; two that share a file (deploy/, a shared README section) run serially, or the second's brief says it merges the first's merged head before its review.
- **Merging back.** Merge `main` in plainly first. Only when a ratchet file like `.test-count` is the sole conflict does `git merge -X theirs origin/main` take `main`'s floor (the next green check raises it), since `-X theirs` also resolves real product conflicts silently (it dropped an import once). After either merge, read every file both sides touched. Before telling an implementer to merge with `-X theirs`, the lead trial-merges (`git merge-tree --write-tree`) and names the conflicting files; only a ratchet-only list allows it.
- **Milestones may overlap,** since every issue lands on `main`: the next milestone starts while the last one's close runs. Waves that share files stay serial across milestones too. Two leads at once run one chat each, in separate checkouts.
- **The check lock.** Milestones that share a machine also share its check lock: cap the implementers running checks across them, or give each milestone its own lock and port range where checks share nothing. The lock admits one test job at a time. It goes to two only once the browser suite is down to its key screens (`references/project-setup.md`) and a measured run, two jobs side by side with check times and load logged in the ledger, shows the machine holds. Measured on a laptop already deep in swap: two full checks at once failed 4 of 6 on timing flakes and ran Playwright 1.8x slower, so one holder stayed; the lever for queue time is a smaller per-round check, not a second holder.

- **In flight is capped by the lock, not by the issue list.** Keep at most the lock's holders plus two issues past implementation at once, smallest first, so a check never waits behind more than one other; start the next issue when one merges. Parallel implementers that all need the lock only move the wait. Watch the queue: when an agent reports "queued for the lock" twice in a row, stop starting work.
