# Skill pause

Step 8 of the run. The procedure (sweep, check, cold read, report, ship) is authoring-skills' "Closing a skill update"; this file holds what's specific to a build milestone. The lead reads this at each milestone's close; the next milestone doesn't wait for it (pre-launch weight: once, at the end of the build).

1. **The ledger's "For the skill" lines.** Question each one (does it hold, is it already encoded, or should it be dropped) and fold the ones that hold into the skill that owns them: process into the SKILL.md body, mechanics into `references/learnings.md`, the run's history and the user's quotes into `references/learnings-archive.md`.
2. **Tallies.** Run `pr-review`'s rules sweep and sum the ledger's readiness tallies. Count Escaped lines by the milestone they came from, across every ledger so far, and set this milestone's count beside the last two: this is the evidence for how much merges without the user. Three zeros in a row is the case for loosening one standing gate, a count above the one before it the case for tightening one, each a proposal for his yes. Without the count, a change in autonomy is a guess.
3. **The user's corrections.** Sort every correction the user made this milestone. One that would hold on another project goes into the skill that owns it (this one, pr-review, hifi-design), plus a CLAUDE.md copy only when implementers need it at build time; one about this product goes into CLAUDE.md alone. For each correction, write the narrow reading, then go one level up and encode the class it belongs to when the class holds (authoring-skills, "Encode a correction one level up").
4. **Prune and test.** Prune this skill and its references (authoring-skills, "Every update prunes too"), cold-read every skill the pause edited, cuts included (authoring-skills, "Cold read"), and run a blind test (authoring-skills, "Testing a rule") on any rule you'd add or cut but aren't sure about.
5. **Show, then push.** Show the proposed edits, cuts next to additions; push on the user's yes. Edits to the project's own files (CLAUDE.md, review rules, build docs) land on `main` like the lead's other doc edits (SKILL, Roles).
6. **Close** with the five-part summary (zero-to-one, "At every step").
