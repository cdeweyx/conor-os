# Design loop

What a build adds around hifi-design's loop for a Design Needed issue, plus the rules for Final that the SKILL summarizes. The lead reads this when a Design Needed loop starts, when a pick moves to Final, when a brief cites a motion spec, and when design feedback arrives mid-build. Whether an issue needs the loop is the Design Needed test (SKILL, Keeping the tracker true).

## The loop

The loop itself is hifi-design's, at the weight its Weights section sets (Full for a surface whose new direction later issues build on, Quick for one built from patterns already on Final): prep, the ideas ask, the direction round, the silent polish loop to the critic bar, the ready review, Lock. This file holds only what a build adds around it.

- **Design runs in its own session.** A Design Needed loop's rounds (planner plans, designer and critic reports, Paper review pages, the user's notes) fill the build lead's context, so each loop runs in a separate design-lead session, a top-level session since a subagent can't spawn the planner, designers and critics. When an issue's loop is about to start, the build lead nudges the user in chat to open a new session for it and hands over the opening prompt (the issue, the inputs, the state so far); the user doesn't have to remember. Handing a loop to another session is a skill pause (SKILL step 8): in the same turn as the nudge, before the opening prompt, fold every learning from the rounds run so far into its owning skill and list them in the message; the user shouldn't have to ask. The design lead posts its asks to the tracker like any lead; the build lead picks the issue back up at lock, from one comment naming the Final artboards and the build brief's design section. Closing a loop is a skill pause too: in the same turn as the lock comment, the design lead folds the loop's learnings into their owning skills and lists them in the closing message, unasked.
- **Check a handoff's premises before asking on them.** A handoff written by another session states facts about what a user can do; check each against the owning issue's settled list before it frames an ask. A handoff once named a way in that the issue had already ruled out, and two asks built on it confused the user.
- **Review size follows pr-review,** and a Small or Medium issue gets one built-surface critic pass. One stamped check per head (`references/loop.md`, step 6).
- **Then move the pick to Final and dispatch the build.** Before a design issue's PR merges, three critics (Model: critic role) score screenshots of the built surface (real data, every state the design drew) against its Final artboards, and a polish round fixes what they find (impeccable polish, better-ui with `references/judge-siblings.md`); it merges only when the built surface scores at least as well as Final.
- **The user sees it when he looks** after the milestone's close, where his notes come back as ordinary issues (`references/review.md`). The exceptions are hifi-design's two looks, the direction pick and the ready review, on a new surface's direction that later issues build on, which wait on him (SKILL, When to stop). A Quick loop doesn't wait for his "good": the lead's pick goes to Final and the build is dispatched, and its ready review rides with the milestone's look, where his notes come back as issues, unless he asks for a round sooner.
- **Tracker state.** Any issue in a design cycle (a Design Needed issue, or a build issue waiting on its canvas revision) carries the Design Needed label. It waits in Todo until its loop starts, then sits in the tracker's In Design status while the loop runs, so the board shows what's actually being designed. When the design is picked and on the Final page, the Design Needed label comes off (the label means design is still owed, not that there was a design loop), and the issue moves to In Progress when the implementer is dispatched: at once, or after the user's go when it's a new surface's direction (SKILL, When to stop). A locked design whose build is still blocked goes back to Todo, not left in In Design. An ask during the loop moves it to Waiting on Me, and once the user answers it returns to In Design, never to In Progress, which means an implementer is on it. A surface designed in parts gets one sub-issue per part under its issue, created the turn the part starts and Done the turn it locks (what locked, where it lives), and the parent keeps a dated "Where it stands" table (part, status, issue) updated at every lock.

## Design feedback mid-build

Design feedback that arrives mid-build, outside an issue's own gate (a reviewer's or critic's note on a surface the current issue doesn't own, the lead's own eye, a user comment mid-run), first gets one question: does it change a constraint (DESIGN.md, a Final artboard, a rule for surfaces)?

- **Yes** is filed as a tracker issue the same turn. A token change is ask-first (SKILL, The lead's own calls) unless the user's note is itself the ask. Then the drift sweep (SKILL, Keeping the tracker true) runs and, when a surface's layout changes, the Design Needed test (a value tweak inside the scale needs neither).
- **No** means one line in `docs/build/papercuts.md` (surface, what, source, date), not a one-off fix in whatever PR is open, since spot fixes made one at a time pull surfaces apart. The close drains the log in one polish pass (step 6, `references/close.md`), and whatever that pass leaves goes into the tracker, which stays the only todo list.

The user's notes after a look aren't build-time feedback; they're filed as step 7 says (`references/review.md`).

## Final and motion specs

Final is the source of truth for what a surface looks like, motion included, except a tweak built from code, which wins until the close's Final pass (step 6). When a brief cites both a Final artboard and a motion spec, the lead reads them against each other at dispatch, and any rule in the spec that changes what a still frame shows (a run that hides at an edge, a label that appears late) either matches Final or gets ruled in the brief, Final winning by default. A moving element is never masked out of its baselines and never judged from one still: frame-sampling behavior tests pin it at several offsets or times, including the awkward ones (a run cut by an edge, mid-transition), and the built-surface critics see frozen frames at those points at the user's own viewport as well as the design's.

**A fresh worker moves a section to Final.** The copy tool doesn't cross files, so each Final artboard is rebuilt from its Explorations twin and pixel-matched, about 15 to 30k tokens apiece. A designer who drew the rounds runs out of context partway through a 40-artboard move (twice, at 1 of 12 and 2 of 48), so the lead hands the move to a fresh worker with the source rows, the PNGs to match, the names and the columns. The cheap way across files is scripting the local Paper server over HTTP (source node to new artboard) rather than relaying each artboard's JSX through the worker's context (40 artboards for about 190k tokens). When a final critic pass leaves only small rulings, the worker applies them during the move instead of a separate fix round, and compares each Final export by eye: only the ruled fixes should differ.

## One element, one look across Final

When a copy pick moves to Final, check its wrap at every width and keep the gaps under it (at 390 a one-line sub change ran three lines and touched the card below; the card moved down instead of the type shrinking), and list any flattened image that still shows the old copy (a dialog's backdrop) rather than leaving it silently stale. Before asking for a token change to fix a layout problem, try the rule that already covers it: a darker scrim didn't stop a dialog cutting the hero sub, and moving the dialog (DESIGN.md's "an overlay never cuts a line of words") did, with no token change. When the user narrows a design lead to one issue, write a handoff file per sibling design issue (what's drawn and settled, what's open, what's shared) and give one paste-ready prompt per issue in its own code block, each naming its handoff file. Handoff files and a design lead's scratch (rulings, plans, critic briefs, stills, motion specs, prototypes) live in the main checkout's ignored `.build/design/<issue>/`, never in a Conductor workspace: archiving one session's workspace took its handoffs, the motion spec and the prototype.

When a pick moves to Final, the designer searches the whole Final page for every artboard that draws that element (by node name and by its text) and updates each in the same move by duplicating the new version into place, never only the artboards the brief lists. The milestone close repeats it as a sweep (the element sweep): every element drawn on more than one Final artboard is compared instance by instance, and a stale one is fixed in the close issue. When the design session's write scope leaves out an artboard that draws the changed element, the lock comment names that artboard for the sweep.

When Final lives in another Paper file, the move is a rebuild (no cross-file duplicate): get_jsx on the source, write_html on the Final page in chunks, two workers split by row, each diffing every text node against its source before it's done. An element the polish found drawn two ways (a ring solid on some artboards, at 35% on others) is fixed to one rule in the same move. Then the lead lays the Final page out to be reviewed before saying it's done: one band per moment (1440 dark and light, 768 dark and light, 390 dark and light, twins side by side), a caption over each band naming the moment, section labels and a read-me. Boards left where the move scripts put them (index × 3200, twins offset) read as scattered.

Exports follow the same split as the Design Needed test: a surface a design loop drew exports once, for the issue that builds it; a tweak never re-exports mid-milestone, and waits for the close's Final pass.
