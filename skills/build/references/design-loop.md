# Design loop

How a Design Needed issue runs, in full, plus the rules for Final that the SKILL summarizes. The lead reads this when a Design Needed loop starts, when a pick moves to Final, when a brief cites a motion spec, and when design feedback arrives mid-build. Whether an issue needs the loop is the Design Needed test (SKILL, Keeping the tracker true).

## The loop

- **Design runs in its own session.** A Design Needed loop's rounds (planner plans, designer and critic reports, Paper review pages, the user's notes) fill the build lead's context, so each loop runs in a separate design-lead session, a top-level session since a subagent can't spawn the planner, designers and critics. When an issue's loop is about to start, the build lead nudges the user in chat to open a new session for it and hands over the opening prompt (the issue, the inputs, the state so far); the user doesn't have to remember. Handing a loop to another session is a skill pause (SKILL step 8): in the same turn as the nudge, before the opening prompt, fold every learning from the rounds run so far into its owning skill and list them in the message; the user shouldn't have to ask. The design lead posts its asks to the tracker like any lead; the build lead picks the issue back up at lock, from one comment naming the Final artboards and the build brief's design section.
- **Resolve his Paper comments once a round answers them.** When a round addresses a comment the user left on a Paper review page, resolve that thread the same turn the round lands (set_comment_thread_status), and list any left open with why; open threads from finished rounds read as outdated asks. A comment status isn't a design write, so it's safe on a file past Paper's size limit.
- **The planner frames every round.** Before any designer draws, the planner role writes the round's plan (Model: planner role): it looks for and parses inspiration, the user's feedback, and the critics' findings, and turns them into a diagnosis, the direction, two distinct takes for two designers, a settled list, and a finish checklist. It runs at round one, at each of the user's looks, and between them. The user's notes are one strong input, not orders: the plan says follow, go further, or push back for each, with the reason. The lead routes the inputs, sends the takes to designers, runs the critics, and picks; it doesn't write the direction.
- **Layout before polish.** Round one's takes differ in composition (centered, split, product-first), measured against the references' own layouts, so the layout is picked before any polish round; no polish round runs while the layout is untested against a real alternative, and the layout pick is the user's: round one's layouts come to him as one quick look before any critic-driven polish, the one exception to sharing work only when it's ready (critics optimized a split he didn't want for four rounds).
- **No chat rounds.** Research for references as needed (Mobbin, the primitive library's docs, explain-interface on a live example), handed to the planner. At least two design agents per round (Model: worker role) draw the planner's two takes on an explorations page in Paper, three critics score them (Model: critic role), the lead picks against the brief and the user's recorded preferences, a design agent polishes the pick, and the critics score the polish. If the pick's median taste is under 8 or the critics split on it, run another round before anything is built.
- **His review page lays the takes out in rows.** One row per take, a label artboard at its left, the same state in the same column across rows, and a read-me naming the calls, on a page made for the review. The chat message opens with the lead's pick in one line ("I'd pick B"), since he asks "A or B?" before reading the evidence.
- **Taste calls are his, drawn both ways.** A ground, color or texture choice goes to him with both takes drawn; the critics' vote and the lead's lean are inputs, not the pick.
- **Designers draw only real data.** Every value a chart or figure shows comes from the code that computes it; a designer may not extend a series past its data, smooth it, or invent a continuation to fill a frame. The designer brief says so, and the lead reads each generator diff for a new seed or constant.
- **A state still must differ from rest.** Self-review compares every state still (hover, pressed, error) against the rest still and fails one that's identical.
- **Start a round in a fresh Paper file once the current one warns.** A review-page copy pushed the Explorations file over Paper's size limit mid-loop; check the warning (list_resources shows it) before a round and open the next file then, not after a write fails.
- **Cap the loop at five rounds.** Every rubric after round one carries the planner's "Settled, don't reopen" list (the user's calls and the lead's rulings), and a finding that reverses one is dropped, along with that critic's score when it was the critic's top finding, since fresh critics can't see earlier rounds and will re-argue them. Past the cap, when median taste doesn't rise between two rounds, or when critics start reversing each other's fixes, the lead rules on the open findings and moves the pick to Final.
- **Review size follows pr-review,** and a Small or Medium issue gets one built-surface critic pass. One stamped check per head (`references/loop.md`, step 6).
- **Then move the pick to Final and dispatch the build.** Before a design issue's PR merges, three critics (Model: critic role) score screenshots of the built surface (real data, every state the design drew) against its Final artboards, and a polish round fixes what they find (impeccable polish, better-ui with `references/judge-siblings.md`); it merges only when the built surface scores at least as well as Final.
- **The user sees it when he looks** after the milestone's close, where his notes come back as ordinary issues (`references/review.md`). The exception is a new surface's direction that later issues build on, which waits on him (SKILL, When to stop). Bring a round to chat only when he asks for one. Never share a draft, one concept, or a critic's interim score as it lands: the work comes to him once, all of it together, when it's ready for review. Detail calls (a token, a copy line, a rest state) wait for a near-final review; a review of direction asks about direction only, and the detail calls ride along unasked until the design is close. A pick that comes with comments ("couple comments, otherwise good") is a go: apply the comments, run a polish pass and the critics, move it to Final, and dispatch the build, with no second review from the user.
- **Tracker state.** Any issue in a design cycle (a Design Needed issue, or a build issue waiting on its canvas revision) carries the Design Needed label. It waits in Todo until its loop starts, then sits in the tracker's In Design status while the loop runs, so the board shows what's actually being designed. When the design is picked and on the Final page, the Design Needed label comes off (the label means design is still owed, not that there was a design loop), and the issue moves to In Progress when the implementer is dispatched: at once, or after the user's go when it's a new surface's direction (SKILL, When to stop).

## Design feedback mid-build

Design feedback that arrives mid-build, outside an issue's own gate (a reviewer's or critic's note on a surface the current issue doesn't own, the lead's own eye, a user comment mid-run), first gets one question: does it change a constraint (DESIGN.md, a Final artboard, a rule for surfaces)?

- **Yes** is filed as a tracker issue the same turn. A token change is ask-first (SKILL, The lead's own calls) unless the user's note is itself the ask. Then the drift sweep (SKILL, Keeping the tracker true) runs and, when a surface's layout changes, the Design Needed test (a value tweak inside the scale needs neither).
- **No** means one line in `docs/build/papercuts.md` (surface, what, source, date), not a one-off fix in whatever PR is open, since spot fixes made one at a time pull surfaces apart. The close drains the log in one polish pass (step 6, `references/close.md`), and whatever that pass leaves goes into the tracker, which stays the only todo list.

The user's notes after a look aren't build-time feedback; they're filed as step 7 says (`references/review.md`).

## Final and motion specs

Final is the source of truth for what a surface looks like, motion included, except a tweak built from code, which wins until the close's Final pass (step 6). When a brief cites both a Final artboard and a motion spec, the lead reads them against each other at dispatch, and any rule in the spec that changes what a still frame shows (a run that hides at an edge, a label that appears late) either matches Final or gets ruled in the brief, Final winning by default. A moving element is never masked out of its baselines and never judged from one still: frame-sampling behavior tests pin it at several offsets or times, including the awkward ones (a run cut by an edge, mid-transition), and the built-surface critics see frozen frames at those points at the user's own viewport as well as the design's.

## One element, one look across Final

When a pick moves to Final, the designer searches the whole Final page for every artboard that draws that element (by node name and by its text) and updates each in the same move by duplicating the new version into place, never only the artboards the brief lists. The milestone close repeats it as a sweep (the element sweep): every element drawn on more than one Final artboard is compared instance by instance, and a stale one is fixed in the close issue.

Exports follow the same split as the Design Needed test: a surface a design loop drew exports once, for the issue that builds it; a tweak never re-exports mid-milestone, and waits for the close's Final pass.
