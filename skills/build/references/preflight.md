# Preflight

Step 3 of the run, in full. A missing input blocks only the issues that need it: ask for it on those issues and dispatch the rest (SKILL, When to stop).

- **The milestone's issues,** with blocked-by relations, pulled over the Linear MCP, in the order they sit in the Linear milestone: that order is the sequence of record, and when the lead resequences, it reorders Linear to match. An issue blocked by one outside the milestone that hasn't reached `main` waits; the rest go on.
- **Group by surface.** Issues that touch the same screen share one branch, one PR and one review, worked as one dispatch: the branch is the first issue's, the PR carries every key, and review sizes it by the group's combined changed lines. Two branches never accept the same baseline in one milestone.
- **Every issue filed right.** Every issue in the milestone is assigned to the user, sits in Todo or later (never unassigned; one the user moved to Backlog sits out this run, so skip it and say so in the digest), and carries a priority, an effort label, a type label and a risk label where one applies (SKILL, Keeping the tracker true); fix any that aren't before the first dispatch. The tracker's create defaults are wrong here.
- **Owed inputs** the README names for this milestone exist: artboard exports (over the Paper MCP), canvas revisions (human design work; ask on the issues that need them, which wait), keys or accounts, for the milestone that first hosts the product, the user's steps in `references/hosting-setup.md`, and for the one that first adds sign-in, `references/auth-setup.md`. Check each brief's artboard names against the canvas (a brief once cut an artboard's name short, "Settings · empty" for "Settings · empty state"), and check that the design's fonts render in the test browser; a missing face makes every baseline wrong.
- **Paper is running before anything needs the canvas.** When it isn't, the lead launches it with `open -a Paper` and opens the file over the MCP, never asking the user to open it. Do it here: an MCP connection forms at session start, so a Paper launched mid-session (or at close) stays unreachable to the session and every agent it spawns until the next session. If the session started without it, run the Final pass first thing next session.
- **The design file's open comments and stale artboards.** List every open comment thread on the design file (all pages, not only the milestone's artboards) and map each to an element and an issue; each is an owed input, worked in the milestone's design loop or filed. Then screenshot every Final artboard the milestone's briefs name and check it against the current pattern on the surfaces that shipped since it was drawn (layout, copy, numbers that agree with each other): a state still on an old layout is owed design, not a spec to build to. Re-list open threads at the start of every turn while a design loop runs; the user comments mid-run.
- **The demo script.** If `docs/build/demo-M<n>.md` doesn't exist, write it from the plan's milestone row (done state, what's runnable, the check) and the briefs' done criteria: setup commands, the commands whose output proves the numbers, then each step on localhost with what it should show. Post it in chat and keep going; the user can redirect it while the run proceeds. It's the target the issues build toward and the script the user follows at review.
- **What waits on the user.** Flag every issue that hits a When to stop item (a one-way door, a first look or product rule) now, and post its ask as soon as there's something to decide on (a one-way door at once, a new surface's direction when the design loop has its pick). A first-look issue isn't grouped with the issues that build on it.
- **The ledger file,** from the template.
- **Done means merged.** Every milestone issue marked Done has a merged implementing PR (a planning PR that names a key closes it).
- **The check is quiet.** The project's check command prints a summary and the failures, not every passing line. If it streams everything, file making it quiet as the milestone's first issue (a Small Chore), since the lead doesn't edit product files; when the check's config is protected, ask for that issue's unlock at preflight and keep dispatching, since the yes is only needed at its merge and nothing else waits on it. Every implementer re-reads that output on each step after.
- **CLAUDE.md carries the machine rules and the not-evidence list** (`references/project-setup.md`), since every prompt points there instead of restating them. Copy in whichever is missing before the first dispatch; it lands like the pause's CLAUDE.md edits.
- **Owns against protected.** Check each brief's Owns list against the project's protected list: tell the implementer where work goes when a brief names a protected file.
